# 《富甲横阳》生活循环 / 活力 / 睡眠 / 状态系统阶段设计

本文固化《富甲横阳》生活循环与轻量状态系统的阶段性共识。文中内容按 **【已确定】**、**【建议】**、**【待验证】** 区分；建议项与测试参考值均不代表最终实现或正式平衡数值。

## 1. 总体设计口径

**【已确定】** 这套系统不是为了把《富甲横阳》做成生存游戏，而是为了形成“吃饭 → 活动 → 消耗 → 休息 → 睡觉 → 再开始一天”的轻生活循环，让餐饮、客栈、休闲、药店、医院、住宅等商业空间真正参与小镇经济。

**【已确定】** 系统需要有生活感，但不能让玩家觉得被体力系统卡住。负面状态用于改变效率、收益或体验节奏，原则上不完全禁止移动、对话、探索或基础经营。

**【已确定】** 当前阶段只整理设计规则，不新增活力字段、状态字段、数据库表、计时器、消费逻辑或正式数值配置。

## 2. 开局据点与横阳客栈

**【已确定】** 横阳客栈是玩家进入横阳后的第一个生活据点，也是新手期认识住宿、休息、NPC、室内交互和白石街出口的教学场所。

**【已确定】** 当前横阳客栈只开放一楼。正式开局流程为：

`创建角色完成 → 在横阳客栈一楼临时客房/侧房醒来 → 可选 1～2 个轻量环境互动 → 进入一楼大堂 → 与陈掌柜首次正式对话 → 离开客栈进入白石街`

**【已确定】** 二楼当前不作为出生点，也不采用“二楼醒来 → 下楼”的开局。二楼只保留楼梯和“装修中 / 暂不开放”的软封锁，为后续剧情、住宿升级或经营扩展预留空间。

**【建议】** 一楼临时客房的轻量环境互动可从查看行李、整理床铺、查看窗外或阅读客栈提示中选择 1～2 个。它们用于建立生活氛围，不应形成强制的新手操作链。

**【待验证】** 一楼临时客房、侧房与大堂之间的具体地图尺寸、移动距离、交互数量和新手提示频率，需要结合后续客栈室内改版进行实际节奏测试。

## 3. 地图开放节奏

**【已确定】** 地图开放采用“新手期强约束 → 中期分阶段多方向开放 → 后期基本自由探索”的节奏。

**【已确定】** 新手期应围绕客栈和白石街建立清晰行动目标，避免玩家在尚未理解移动、对话、任务、商店和休息规则前进入过多区域。

**【已确定】** 中期可随主线、关系、经营进度或城市事件逐步开放多个方向；后期以自由探索为主，只在剧情、施工、营业时间或特殊事件确有需要时设置限制。

**【建议】** 区域开放条件优先使用现有任务、关系、事件和世界配置表达，避免为每个路口编写专用代码。

**【待验证】** 新手强约束持续多久、每阶段开放多少出口，以及提示方式采用 NPC 引导、路障还是任务条件，需要通过完整新手流程测试确定。

## 4. 玩家基础属性

**【已确定】** 玩家基础属性保持轻量，不走传统战斗 RPG 的力量、敏捷、防御、暴击等战斗属性路线。属性应服务于生活、经营、探索、社交和制作。

**【建议】** “见识”“人缘”“手艺”可作为候选长期成长属性：见识关联探索与信息，人缘关联社交与商业往来，手艺关联制作与服务。当前不落地字段、数值或升级规则。

**【待验证】** 是否需要全部三项、是否对玩家直接显示、如何成长以及如何影响任务或经营，需要在相关玩法成型后验证。

## 5. 活力值与消耗原则

**【已确定】** 活力值作为主要日常状态数值，用于连接活动消耗、饮食、住宿、休闲服务与睡眠。

**【建议】** 活力可采用容易理解的 `0～100` 显示范围，但当前不作为正式字段或最终数值上限。

**【已确定】** 普通走路、查看界面、基础对话和一般街道探索不消耗活力。只有高强度、长时间或具有明确收益的活动才考虑消耗，例如高强度劳动、连续制作、特殊探索、经营加速或部分小游戏。

**【已确定】** 活力不足时优先降低效率、收益或连续高强度活动能力，不应把玩家完全锁在原地，也不应阻止基础对话和正常回家休息。

**【建议】** 消耗提示应让玩家在开始高强度活动前知道成本，避免活动完成后突然扣除大量活力。

**【待验证】** 活力上限、各活动消耗、低活力阈值、恢复速度和效率折损比例均需通过实际游戏节奏验证。

## 6. 饮食、住宿与休闲服务

**【已确定】** 饮食、住宿和休闲服务应成为活力恢复与日常消费的重要驱动力，让餐馆、小吃店、客栈、足浴、按摩、药店、医院和住宅拥有持续用途。

**【已确定】** 不同恢复方式应体现不同耗时感：普通食物适合快速补充，正餐恢复更明显，足浴和按摩需要等待一段服务时间，睡眠承担跨时段和离线恢复。

**【已确定】** 普通食物以恢复活力为主。少量滋补品或药品可以提供轻量 Buff，但不应让普通饮食失去价值，也不应演变为复杂药剂堆叠系统。

**【建议】** 快速食物、正餐、休闲服务和睡眠可形成“便利程度、恢复量、价格、耗时”之间的差异，让玩家按当时计划选择，而非永远只有一个最优选项。

**【待验证】** 以下仅为原型测试参考，不是正式平衡值：

- 小吃恢复活力约 `+10～15`；
- 正餐恢复活力约 `+25～35`；
- 按摩或足浴恢复活力约 `+25～40`；
- 一次服务耗时约 `5～10 分钟`；
- 不同睡眠时长的恢复量，以及提前结束睡眠时的恢复折损。

## 7. 睡眠与离线完成

**【已确定】** 睡眠采用真实时间计时，并允许玩家离线后继续完成。玩家开始睡眠后不需要保持游戏前台运行。

**【已确定】** 服务端时间应作为睡眠完成与奖励结算的权威依据，避免客户端改时间获得异常收益。具体实现仍需遵守现有存档兼容与 requestId 幂等原则。

**【已确定】** 睡眠是生活循环的重要组成部分，但不能成为每天必须长时间等待才能继续游玩的硬门槛。

**【建议】** 玩家可根据计划选择短休息、正常睡眠或较长睡眠；提前结束可以获得已经完成部分的恢复，但可能存在合理折损。

**【待验证】** 最短睡眠时长、完整睡眠时长、离线结算频率、提前结束折损、跨日处理和异常断线恢复规则需要原型验证后确定。

## 8. 轻量状态与 Buff 规则

**【已确定】** 状态系统保持轻量，第一阶段候选状态包括“睡眠不足”“疲劳”“感冒”“精神饱满”等能够直接理解的生活状态。

**【已确定】** 同类 Buff 或状态原则上不叠加；更强状态替换较弱状态，避免玩家维护复杂层数和计时列表。

**【已确定】** 负面状态只影响效率，不完全禁止行动。例如疲劳可以降低高强度活动效率，感冒可以降低恢复或工作收益，但玩家仍能走路、对话、购物和返回住所。

**【建议】** 状态界面只展示名称、主要影响和剩余时间，避免加入大量隐藏参数。恢复手段应与对应商业空间形成自然联系，例如休息缓解疲劳、药店处理轻症、医院处理较重状态。

**【待验证】** 状态触发概率、持续时间、强弱等级、替换优先级、效率影响幅度及是否允许少量互不相同的状态并存，均需在系统原型中验证。

## 9. 实施边界与后续验证

**【已确定】** 后续实现应优先配置驱动，并保持 Web 与微信共享同一套状态、计时和结算规则。涉及玩家状态保存时采用新增字段与默认值，保证旧存档兼容。

**【已确定】** 本文不要求当前客栈室内、地图、数据库或 UI 立即返工。新增功能应按“数据结构 → 最小服务端规则 → 共享客户端反馈 → 定向测试 → 人工节奏验收”的顺序逐步落地。

**【待验证】** 第一轮原型应重点回答：玩家是否愿意主动消费恢复、低活力是否仍可正常游玩、离线睡眠是否清晰可靠、不同恢复方式是否各有用途，以及生活循环是否增加乐趣而非操作负担。
